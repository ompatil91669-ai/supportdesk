## 1. Learning outcomes

Understand and implement pagination, filtering, search, sorting, comments endpoints, OpenAPI documentation, unit tests, integration tests, mocks, test databases, code coverage and Definition of Done (DoD).

- **Pagination:** return a limited subset of records at a time.
- **Filtering:** narrow results by fields such as status, priority or assignee.
- **Search:** find records using an approved search term.
- **Sorting:** control the order of returned records.
- **OpenAPI:** standard format for describing HTTP APIs.
- **Unit test:** test one unit of logic in isolation.
- **Integration test:** test multiple parts working together.
- **Mock:** replace a dependency with a controlled test substitute.
- **DoD:** agreed conditions that must be met before work is complete.

## 5. Step 2 — Design ticket query parameters

Use query parameters rather than creating a separate endpoint for every filter, unless the existing API design requires otherwise.

Illustrative request:

```
GET /api/tickets?page=1&limit=10&status=open&priority=P1&assigneeId=user-123&search=payment&sortBy=createdAt&sortOrder=desc
```

Adapt the route prefix and parameter names to the existing project.

| Feature | Example | Expected behaviour |
| --- | --- | --- |
| Pagination | page=1, limit=10 | Return first page with at most 10 records |
| Status filter | status=open | Return only open tickets |
| Priority filter | priority=P1 | Return only P1 tickets |
| Assignee filter | assigneeId=user-123 | Return tickets assigned to that user |
| Search | search=payment | Search only approved searchable fields |
| Sorting | createdAt, desc | Newest records first |

### Pagination metadata

Keep the existing response envelope. A possible metadata shape is:

```json
{
  "data": { "tickets": [] },
  "error": null,
  "meta": {
    "page": 1,
    "limit": 10,
    "total": 42,
    "totalPages": 5
  }
}
```

This is an example, not a mandate to change the project's established response structure. Confirm the final shape with the lead.

### Validation and safety

- Reject invalid page numbers and limits.
- Apply a sensible maximum page size approved by the lead.
- Allowlist sortable fields; never pass arbitrary client input into a database sort expression.
- Validate filter values against actual enums/schema.
- Use parameterized ORM queries; do not concatenate raw SQL from user input.
- Apply customer ownership scope before returning results.
- Ensure pagination totals use the same access scope as returned records.

## 6. Step 3 — Implement filters, search and sorting

Implement the query flow through the established layers:

**Route → Controller → Service → Repository**

- Route: map URL to controller and attach validation/auth middleware.
- Controller: read validated query parameters and send the HTTP response.
- Service: apply business rules, including role-based data scope.
- Repository: build the database query and return records/counts.

Do not put Prisma calls in routes, controllers or services. Database access belongs in repositories/.

Create an OpenAPI specification in the project's documentation/API-docs location, following repository convention. Expose the interactive documentation at:

```

```

- Health endpoint.

- Ticket list and detail.

- Comments create/list.
- Authentication requirements.
- Query parameters for pagination, filters, search and sorting.
- Request body schemas.

Documentation accuracy rules:

- Document only routes that actually exist.
- Do not claim a response field exists unless the API returns it.
- Match required/optional fields to actual validators and database constraints.
- Include Bearer authentication configuration for protected endpoints.
- Use fictional examples only; never put real tokens, secrets or personal data in the spec.

## 10. Step 7 — Jest unit tests for services

Write service unit tests with repository dependencies mocked.

Cover:

- Default pagination behaviour.
- Valid and invalid filter combinations.
- Search and sorting validation.
- Customer scope is applied.
- Agent scope is applied.
- Comment creation success.
- Comment creation for a missing ticket.
- Invalid comment operations as represented by service rules.
- Error propagation from repository failures.

Unit tests must not connect to the real database. Mock the repository boundary and assert the service passes the correct query/scope and handles results correctly. Test observable behaviour, not private implementation details.

## 11. Step 8 — Supertest integration tests with a test database

Use Supertest to exercise the real Express application through HTTP requests. Run integration tests against a dedicated test database, never production or a shared live database.

Minimum integration coverage:

| Area | Scenario | Expected result |
| --- | --- | --- |
| Ticket pagination | Request first page with small limit | Correct page and metadata |
| Ticket filters | Filter by status | Only matching tickets |
| Priority filter | Filter by priority | Only matching priority |
| Assignee filter | Filter by assignee | Only matching assignee |
| Search | Search a known test term | Matching tickets returned |
| Sorting | Sort newest first | Correct order |
| Invalid query | Invalid page/limit/filter/sort field | 400 validation response |
| Customer scope | Customer lists tickets | Own tickets only |
| Cross-customer access | Customer requests another user's ticket | No data leakage |
| Agent scope | Agent lists tickets | All tickets in approved scope |
| Comments | Create a valid comment | Success and correct author |
| Missing ticket | Comment on non-existent ticket | 404 |
| Comment validation | Empty/invalid comment body | 400 |
| Auth | Missing token on protected endpoint | 401 |
| Role | Wrong role on restricted route | 403 |
| Documentation | Request /docs | Documentation UI renders |

Use deterministic fixtures/seed data so tests do not depend on execution order or external services. Clean up test records safely. Keep test database configuration separate from development configuration.

## 18. Term of the day — DoD (Definition of Done)

**Definition of Done (DoD)** is the agreed checklist that proves a task is complete and ready for review. It prevents a feature from being called “done” just because code was written.

For today's task, code alone is not enough: query behaviour, access control, comments, documentation, automated tests, test count and coverage must all meet the acceptance criteria.
